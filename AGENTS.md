## Branching

- `develop` is the **only development and engineering channel**, including cybersecurity, dependency maintenance and infrastructure corrections. All implementation work is integrated here; direct commits are allowed after the local quality gate, and every applicable push runs CI.
- `main` is the final release branch and repository default. Implementation integrates only through the final PR **develop → main**, after green current local, unit/database/RLS and full PR Playwright evidence and the mandatory ADR-042 Compute Engine decision. **new_coverage >=60%** is required on the PR and on the real main revision before production publication; a PR measurement does not prove main coverage. Missing, pending, cancelled or inconclusive required checks block. Direct implementation/push, history rewriting and bypasses remain forbidden. The main analysis runs after the merge while automatic publication is suspended; publication waits for its real result. See `docs/adr/ADR-042-cobertura-minima-60-publicacao.md`.
- **Two published Git branches only:** `develop` and `main`. Do not create or publish permanent feature, engineering or Dependabot branches. Repository ruleset `24347682` (`Only develop and main branches`) forbids creation of every other branch, with no bypass actors. Dependency changes must be applied and tested in `develop`. Existing local WIP and recovery bundles retain their custody; this policy does not authorize discarding uncommitted work.
- **Two permanent Neon branches only:** `develop` (`br-small-hill-aymcu14y`) and `production` (`br-snowy-violet-aymcvvvv`, default). Do not retain per-feature or per-Dependabot preview databases. Isolated CI copies are temporary execution resources: identify them by run, set the 24-hour expiry, and discard them after the tests with GET 404 proof and independent identity/absence verification. They are not additional development channels. Production data is never a test target. The old Hostinger preview and other persistent preview copies were removed under the explicit two-service cleanup authorization on 2026-10-02.
- Never force-push, rebase, or amend commits already pushed to any published branch.
- Main protection in ruleset `24333849` retains PRs, up-to-date **verify-release** and **scan + cobertura** checks from GitHub Actions, no deletion/force push and an empty bypass list. **ADR-042, human decision 2026-10-06, replaces the 80% minimum with 60% and authorizes removal of the coverage-conditioned update freeze and required main-coverage-mirror.** Baseline/mirror remain observations; unknown provenance is never turned into a main verdict. The before/after ruleset and actual application are recorded in `docs/evidence/release-unblock-2026-10-06/`; the expiry of ADR-037 alone never removes protection. Other debts, including DBT-64, are not closed by this policy change.
- Whenever `main` moves ahead of `develop` after the final release PR, merge `main` back into `develop` immediately. A `develop` that falls behind the release line redeploys stale configuration and hides drift — PR #42's Vercel fix only turned `develop` deployments green after the back-merge.

## Local quality gate (definition of done)

- Before pushing, run `npm run check` and keep it green. It chains `m02:lockfile-guard`, `guard:upgrade`, `check:migration-toolchain`, `guard:contracts`, `m02:work-package-guard`, `m02:debts-guard`, `m02:temporal-guard`, `m02:state:check`, `m02:boundaries`, `m02:secrets-audit`, `guard:mcp-runtime`, `m02:seal-dts:check`, `m02:matrix:check`, `check:ui-stack`, `check:no-supabase-runtime`, `format:check`, `lint`, `typecheck`, `test`, `build`, and `check:bundle`.
- The CI `verify` job (`.github/workflows/ui-stack.yml`; check context `verify-release` on PR/dispatch, `verify` on push) runs **18 dos 20** scripts da cadeia `check` como passos diretos, mais `npm audit --audit-level=high`, e — **em tiers** — `db:test`/`db:check` (diff de banco) e Playwright e2e (chromium+mobile no push, +firefox+webkit no PR); a matriz completa roda em **todo PR** e no `workflow_dispatch`. A push that skips the local gate wastes a CI cycle; treat any red as debt, never as noise.

- **Playwright preparation (C27 / DBT-68/79):** `prepare-browsers` on Ubuntu 24.04 keeps its 12-minute budget and caches the complete kit (all three browsers plus the exact changed Linux package archives). Reuse requires the same lockfile, Playwright version, runner ImageOS/ImageVersion, architecture and verifier version; there are no fallback cache keys. Every run creates a new attestation binding the source SHA, run ID/attempt and manifest SHA256. `verify` retains its 12-minute budget, rejects stale attestations or incomplete/corrupt package payloads, installs with `--no-download --no-remove`, and runs the existing matrix. A cache miss prepares the full resource before saving it. Total runner time includes both jobs; preparation success does not prove E2E success. Required release evidence uses `verify-release`; a push `verify` cannot substitute for the full PR matrix. Closure of DBT-79 requires an observed exact cache hit followed by the complete current PR matrix within both budgets.
- **Cota de Actions:** o job pesado custa **~9,7 min de runner por execução real** (média de 8 execuções verdes medidas: 497-605 s; os 5 runs bloqueados de 3-6 s da cota **não** entram na conta — média contaminada por eles daria ~6 min, que é o número que estava aqui antes), e um push em rajada cria uma execução por commit — sem cobrança por caminho, um dia de trabalho consome a cota do mês. Por isso o `verify` roda em **tiers**, e o `concurrency` cancela o run superseded da mesma ref. **Nenhum teste foi removido, nenhuma regra afrouxada, nenhum orçamento renegociado:** o que mudou foi *onde* cada verificação roda.
- **Three CI pipelines, selected by changed paths:**
  - **Heavy — `UI stack`** (`.github/workflows/ui-stack.yml`): every pull request, plus pushes to `main`/`develop` whose changed files are **not** all under `docs/evidence/**` (`paths-ignore`). Também aceita `workflow_dispatch` para um run completo sob demanda.
  - **Tiers dentro do `verify`** (escopo por `git diff`, fail-closed — base desconhecida ⇒ tudo roda): **sempre que a heavy é disparada** rodam as guardas, `format:check`, `lint`, `typecheck`, `npm run test`, `build`, `check:bundle` e o audit (o *disparo* é que é filtrado por caminho — docs-only vai para a light); **`db:test`/`db:check`** só quando o diff toca `drizzle/`, `src/db/`, `src/server/repositories/`, `src/server/services/`, `scripts/db/` ou os manifests, e o pulo é **visível** (`::notice`), nunca silencioso; **e2e** roda **chromium+mobile** em push e **firefox+webkit+mobile** em PR e no dispatch. A fronteira de release é o **PR**: todo PR roda a matriz completa.
  - **Light — `CI light (docs/evidence)`** (`.github/workflows/ci-light.yml`): pushes and pull requests whose changed files are **all** under `docs/evidence/**` — runs `scripts/m02-lockfile-guard.mjs`, `scripts/m02-work-package-guard.mjs`, `scripts/m02-debts-guard.mjs`, `scripts/m02-temporal-guard.mjs`, `scripts/m02-state-check.ts`, `scripts/m02-secrets-audit.ts` and `prettier --check` on the changed files only. The temporal guard and the ledger state check are the **two steps without the scope `if:`** — by design: their surface is the root ledger and the human queue, so a mixed push that no-ops the other steps still has to keep the live prose and the state marker honest. It installs **no** dependencies: the scripts import node built-ins only, and `m02-state-check.ts` imports its sibling with an **explicit `.ts` extension** because the Node ESM resolver requires it under bare `node` — an extension-less specifier typechecks and passes under `tsx`, and fails only in the light pipeline, which is where nobody looks. A mixed push (code + docs) belongs to the heavy pipeline; the light job's scope guard exits without work instead of failing. **Coverage guarantee:** the two filters are exhaustive for pushes to `main`/`develop` — docs-only runs the light with the contract guard, any other change (including a mixed push, which triggers both with the light no-opping) runs the heavy `verify`, and a code-only push never triggers the light at all. The formatter is resolved from the **lockfile** (`package-lock.json`), never from the `package.json` range: a caret range resolved to a different release than `npm ci` installs, so the light pipeline drifted from `npm run format:check` and failed docs-only pushes the repo's own gate accepted.
  - **Análise — SonarCloud (scanner + cobertura)** (`.github/workflows/sonar.yml`): every PR and main push except docs/evidence-only. The suite generates nonempty LCOV; the scanner must consume its coverage sensor and explicitly attribute PR versus main. **ADR-042: scanner qualitygate.wait=false separates submission from the mandatory gate-readout**, which waits for the same real CE task for at most 300 seconds, verifies project/revision/surface and enforces **new_coverage >=60%**. Raw provider status/conditions remain intact, including an ERROR from its old 80% preset. Security, reliability, maintainability, duplication, hotspots and other failed controls still veto release. Null metric, ignored condition, wrong identity and pending/timeout are NO-VERDICT. Baselines and main-coverage-mirror retain their original verdicts as informational observations; neither proves current main coverage. No test, audit, scanner sensor or job budget is removed.
  - **Espelho observacional sem falso verde (2026-10-07):** o job `main-coverage-mirror` não usa `continue-on-error`. `scripts/sonar/mirror-observation.ts adapter|mirror` executa os CLIs originais, conserva o exit/status bruto e valida o relatório antes de classificar a observação. A ausência verificada da proveniência histórica de main permanece `NO-VERDICT`, sem crédito de cobertura, em resumo e recibos `c29-*-observation.json`; falha de execução, identidade, relatório ou artefato permanece bloqueante. O CE obrigatório não passa por esse classificador e conserva seus exits 1/2 de veto.
  - **`checked === discovered`** (`DBT-62`): `scripts/lib/m02-ci-coverage.ts` assere que **todo** workflow em `.github/workflows/` está ou **coberto** por asserção (`ui-stack.yml`, `ci-light.yml`, `sonar.yml`) ou **declarado fora do contrato com motivo nomeado** (os quatro do Neon) — fail-closed nas duas direções: workflow novo sem declaração reprova, e workflow declarado ausente do disco também. Antes disto o `sonar.yml` era invisível: nem a tabela nem `auditCoverage` o conheciam. O caminho do lcov é declarado em três lugares (`.sonarcloud.properties`, o workflow e `test:coverage`) e a consistência entre eles é passo do `local-ci.sh` (`npm run sonar:lcov-path`) — divergir ali é silencioso e é o modo de falha do `DBT-57`.
  - **Veredito do CE observado:** `scripts/sonar/gate-readout.ts` validates report-task origin/project/task, waits for its completion, verifies provider SHA and PR/main identity, and preserves conditions in the artifact. `releasePolicy` applies ADR-042 minimum 60% without modifying the provider verdict; exit 0 means that explicit policy passed, 1 means policy ERROR, and 2 means NO-VERDICT/precondition. Token remains in the runner; missing metric is null, never zero. PR and main verdicts remain separate. **S6-R2: um NO-VERDICT conserva no relatório a observação do provedor que já passou pela validação** (identidade + veredito bruto do CE) — a ausência de veredito de release nunca apaga evidência validada — e o passo que nomeia a release fixa `shell: bash` com `BASH_ENV: ""`; a auditoria recusa nele qualquer `continue-on-error` (literal ou por expressão), shell customizado, `BASH_ENV` injetável e comandos que engolem erro.
  - Neither filter applies to code: anything under `src/**`, `scripts/**`, `.github/**` or the manifests always goes through the heavy pipeline.
  - **Provisionamento da fixture Neon de PR (S6-R2):** `.github/workflows/neon-pr-branch.yml` cria a cópia pela **API REST oficial** (`scripts/ci/provision-neon-fixture.ts`), não por wrapper de action: `init_source: "parent-schema"` (a branch criada é **CHILD** de pai explícito — `production` para PRs de release (base main), `develop` nos demais — com o schema copiado sem linhas herdadas; a cópia ROOT schema-only é recusada pelo provedor em projetos com papéis SQL-created de *legacy web access* como `app_runtime`, HTTP 412 observado nas runs `37556250921`/`37634147956` e no diagnóstico de console de 2026-10-07, request `bba50fbd-1e38-49d7-a52b-084e5b6e95ed`, evidência em `docs/evidence/neon-parent-schema-2026-10-07/`) e **TTL de 24h dentro do próprio POST** (rede de segurança quando o `branch_id` não chega ao cleanup). O `branch_id` é entregue ao job de cleanup **antes** de qualquer espera por compute/URI; sem retry que caia em cópia de dados. Cada URI recebe `::add-mask::` **na chegada** (antes de qualquer arquivo privado em `RUNNER_TEMP`, modo 0600), e todo valor já conhecido é redigido da mensagem de erro **antes** de ser persistido; recusas do provedor expõem somente status/código (ex.: HTTP 412), nunca corpo bruto. As URIs são fixadas com **porta 5432 explícita e query somente-sslmode** — o destino efetivo do driver não pode ser movido por `PGPORT` ou por parâmetros de query (`host`, `hostaddr`, `port`, `options`), e `assertConnectionPair` recusa o par sem essas propriedades.
  - **Runner limpo do provisionamento Neon (2026-10-07):** `npm ci --ignore-scripts` precede a chamada `tsx`; cache npm não instala `node_modules`. O POST pede também `endpoints: [{ type: "read_write" }]`, pois omitir essa lista cria uma branch sem compute. HTTP 412 é recusa de precondição, nunca diagnóstico automático de quota: somente status/código seguro são persistidos, sem corpo bruto, repetição de POST ou fallback para cópia de dados.
  - **URIs de todas as cópias Neon (2026-10-07):** `pinConnection` e `MaskedSecrets` vivem no helper compartilhado `scripts/ci/neon-resource.ts`, sem aliases no provisionador. O PR, readiness e o consumidor `connections` do drill normalizam a saída da API/action antes de `assertConnectionPair`; porta estrangeira ou query fora de sslmode continua recusada. Readiness mascara valores brutos/canônicos/senha antes de usar ou persistir, prova ambas as conexões e exporta o par canônico para as etapas SQL pelo `GITHUB_ENV` em modo0600, sem overrides posteriores com URI bruta. Masks escapam `%`/CR/LF sem alterar a identidade usada na redação. O provisionamento aceita somente bases main/develop; outras bases abortam.
  - **Ownership do endpoint readiness (2026-10-07):** o passo de prova reutiliza `NeonResources.connections` com `resourcePlan`, ID/ownership da adoção e checkpoint/expiry do prepare. O GET de branch e de endpoints vincula o hostname à branch/projeto do próprio run antes de qualquer conexão PostgreSQL ou export; a prova `connection-identity-verified` integra `connection-contract.json`. Um par internamente consistente de outra branch, falha de API ou identidade inconclusiva aborta sem SQL/export; máscaras e arquivos privados permanecem obrigatórios.
  - **Cleanup Neon de PR:** `.github/workflows/neon-pr-branch.yml` confirma descarte somente por GET HTTP `404` após delete. HTTP `200` reprova com exit `1`; `403`, falha de rede (`000`) e `branch_id` ausente são `NO-VERDICT`/exit `2`, nunca prova de ausência. O próprio passo executa quatro fixtures (`404/403/200/000`) que verificam código e rótulo antes da leitura real. O resumo conserva estado inconclusivo e o job reprova; uma branch sem ID não é presumida inexistente. O limite de branches é precondição externa: liberar capacidade exige identificar e autorizar o descarte, nunca reutilizar banco compartilhado para forçar o CI verde.
  - **Continuidade da prova Neon (2026-10-07):** o passo de prova tem seu próprio `if: always()` e executa o GET mesmo após falha do delete; falha do delete continua falha do job. Summary e comentário mostram outcomes reais de fixture, migrations, integração, E2E e delete, sem presumir que uma etapa pulada executou. Branch_id ausente conserva exit 2.
- **Protocolo de bloqueio de CI (precondição de ambiente externo, item 17 estendido):** quando a plataforma recusar iniciar jobs (cota/billing, anotação do check-run citando *spending limit*), o CI é uma **precondição não satisfeita**, não um veredito — e vale: (a) o `npm run check` local é o **fallback declarado**; (b) todo land durante o bloqueio entra no **ledger de janela sem verificação** com os SHAs enumerados; (c) **nenhum selo cita run inexistente** — selo com `run@sha` só depois de existir run; (d) o primeiro push pós-desbloqueio roda a **varredura de verificação** da janela antes de qualquer land novo; (e) manter **alertas de spending** (50/75/90/100%) ligados, para o esgotamento se anunciar antes de bloquear. Registrar a causa pela anotação da plataforma, nunca por inferência.
- **Run `cancelled` não é evidência** — nem verde nem vermelho — para a regra `run@sha`; a delegação por run no-op continua exigindo **≥ 1 check aplicável** no mesmo commit.
- Never claim work is done with a red gate, and never delete, skip, or loosen a test, lint rule, or budget to force a green.

## Dependency discipline

- **TanStack security floor (2026-10-02):** `@tanstack/react-start` must resolve to `>=1.168.60` and `@tanstack/start-server-core` to `>=1.169.39` (GHSA-qx66-fv34-fjm8 / CVE-2026-102989). Keep Start, Router and router-plugin on compatible published pins; the resolved-family guard remains required. Vercel rejected the vulnerable 1.168.49 before build. Do not enable the vendor bypass variable; upgrade and validate the preview instead. The root Start minimum is enforced by `scripts/dependency-policy.json`.

- `guard:upgrade` também valida as famílias **resolvidas** no lockfile (`scripts/lib/dependency-family-guard.ts`): React/react-dom com versão exata igual; types na mesma linha major.minor; Router/Start/plugin pelas dependências exatas publicadas de react-router/router-core e sem cópias aninhadas divergentes. Negativos vêm dos lockfiles dos PRs #56/#53 por SHA; grupos do Dependabot não substituem esta guarda. O canal manual do DBT-67 reutiliza `neon-drill-ops` com `operation=exercise-provisioning`, ref main/develop, `confirm=true`, action candidata pinada, identidade isolada, expires-at, cleanup always e GET 404; execução real só no Ciclo 25.
- Every `package.json` change ships with a synchronized `package-lock.json` in the same commit. CI installs with `npm ci --ignore-scripts` and hard-fails (`EUSAGE`) on lockfile drift — this exact mismatch broke PR #42's install step.
- Do not assume a library is available because it is common: confirm it in `package.json`/lockfile first, and match the version and idiom already in use.

## Local database

- `npm run db:up` / `npm run db:down` manage a Docker `postgres:17-alpine` container that mirrors CI (`docker-compose.yml`); see `docs/runbooks/postgres-local-docker.md`.
- `npm run db:test` is self-contained against that container with `DATABASE_URL`/`DATABASE_ADMIN_URL` pointing at `127.0.0.1:5432` and `DATABASE_DRIVER=node-postgres`.
- Author migrations with `npm run db:generate` (drizzle-kit), validate them with `npm run db:check`, and exercise them with `npm run db:test` — always against the local container.
- Classifique toda migration no registry sidecar (`scripts/db/migration-classes.ts`) e valide com `npm run db:classify:check` (prepend do `db:test`); a política expand/contract está em `docs/runbooks/migration-safety.md`.
- `scripts/env-guard.mjs` runs as a pre-hook on dev/test/build/db commands. The **production** Neon endpoint is denied unconditionally — no override reopens it. The denylist is `PRODUCTION_ENDPOINT_PREFIX`, mirrored (deliberately, per convention) in `env-guard.mjs:50`, `src/test/helpers/db-precondition.ts`, `m02-cutover-t0.mjs:36`, `m02-role-membership.mjs:27` and `rls-probe.mjs:45`; the guard is a standalone pre-hook that runs before any import, so there is no shared module to extract without reordering boot. Any **other** remote target requires `ALLOW_REMOTE_DB=<motivo>` carrying a **non-empty reason** — never a boolean, and never an ambient leftover: the value is a sentence the CI writes per step, naming the ephemeral branch it is on (`neon-pr-branch.yml`, §26). A predicate that reads `=== "true"` cannot match that, and a grant that cannot fire is worse than none. `dbPrecondition()` (the DB test precondition) enforces the same pair and **keeps the production denylay even when a reason is present** — it repeats it on purpose, because `npx vitest` does not go through the pre-hook and that is the only gate standing in that path. The override waives *loopback*, which is what it exists for; it does not waive the required `DATABASE_ADMIN_URL` + `DATABASE_URL` pair, URL validity, or production. The same policy is implemented once for the `scripts/db/` layer in `scripts/lib/db-target.ts` (`classificarAlvo` returns the decision, `exigirAlvoDeBanco` throws) — it replaced four copies of `assertLoopback`, three of them byte-identical, and those copies were *narrower* than `isLoopbackUrl` (they rejected spellings libpq accepts, such as `127.1`), which is the class of defect duplication produces. Do not reintroduce a local loopback check in a `scripts/db/` file: extend the shared policy, and extend its negative tests with it.

## Security baseline

- The Content Security Policy in `src/start.ts` is strict (`script-src 'self'`). Never add `'unsafe-inline'` or new hosts without first verifying the package's actual runtime behavior in its published dist and documenting that evidence in the PR. (PR #42 lesson: `@vercel/analytics` injects an external same-origin script via DOM — the strict CSP already covered it, and the proposed relaxation was reverted.)

- **Taxonomia de veredicto:** **CORR** = *claim* corrigida pelo S6; **N** = defeito novo encontrado (pode existir com `0 CORR`); "correções forçadas" = CORR + N corrigidos. Os dois números vão **nomeados** no journal — contar só CORR subnotifica o custo do S6. Os bounds do SDD (`bound 2`) limitam **rodadas de correção de um WP**, não a quantidade de claims corrigidas num veredicto.
- O S6 é lane adversarial de **contexto limpo** com `0 REJECTED`; `UNVERIFIABLE` exige declaração no selo e **não** conta como verificado; os N **corrigidos** ficam na §7 do selo e os **declarados** na §Riscos, nunca omitidos. `UNVERIFIABLE` é reservado a **inverificabilidade de princípio** (estado externo inalcançável): ausência verificável por grep/introspecção é `REJECTED` ou defeito declarado, nunca `U`.
- **Elegibilidade no placar (187 itens):** a unidade é o **sub-item** — `15` são sete linhas, `25` são sete; **cluster não é unidade de placar**. Promoção a `DONE` exige a **conjunção** de todos os sub-itens exigidos (maioria, "quase tudo" ou "o principal" não promovem); `PARTIAL` exige **delta nomeado** ("falta X") e sem ele é inválido; o denominador é **fixo em 187** (item inaplicável vira `NA` dentro dos 187, nunca sai da conta); a fórmula é **congelada** em `(D + ½·P)/187`; e o **escritor do placar é o MAESTRO** — work package mede e **propõe**, nunca promove. Evidência de classe é **comando pré-registrado antes da medição**, e ausência **verificável** (grep, `ls`, API de estado de recurso) é `NS`, nunca `UNVERIFIABLE` — `U` é reservado a inverificabilidade **de princípio**.
- **Calibração do S6:** os probes plantados de `REJECTED`/`UNVERIFIABLE` rodam em **série separada** dos reviews reais (periodicamente ou a cada troca de revisor), para calibrar a lane sem contaminar a evidência de um WP; a densidade de achados por WP vai para o journal e é lida como série, não como ponto.

## Session boot and progress journal

- `docs/evidence/agent-state/PROGRESS.md` is the **session handoff**: one file, pointers only (paths, SHAs, timestamps, env **names**), never secret values and never long content. A new model reads it and resumes without agent memory.
- **Boot protocol (~30 s), in this order:** (1) read `PROGRESS.md`; (2) verify the parent-pinned marker in `EXECUTION-STATE-PROGRAM.md` (`npm run m02:state:check`); (3) check watchers and their marker files' last signal; (4) **reconcile** the world first (git refs, artifacts, deployments) — never re-execute blindly; (5) resume from the declared phase.
- **Write protocol:** record intent (`▶`) **before** any mutation and result (`✔`/`✘`) **after**, append-only. An orphan intent means the next boot must reconcile before acting.
- **Milestones:** commit the journal at every phase boundary; the maximum acceptable loss is re-executing from the last milestone (declared, never implicit).
- **Agent memory is an invalidatable cache:** nothing that belongs in an artifact or in the journal is written to agent memory — journal + ledger are the source of truth. Memory carries at most a boot index pointing here.
