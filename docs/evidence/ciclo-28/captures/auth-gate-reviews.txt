## Avaliação do gate atual

1. **Autenticação e identidade reais:** `authentication.ts:43-50` exige um POST de UI para `/api/auth/sign-in/email` com status `200`. Em `:52-66`, `page.request.get('/api/auth/get-session')` consulta o servidor; o assert exige sessão não nula e e-mail do usuário igual à identidade submetida. A implementação instalada de Playwright confirma que a API do BrowserContext lê e atualiza os mesmos cookies do contexto (`playwright-core/lib/coreBundle.js:26198-26239`). Não há mock de login, sessão ou corpo no positivo/negativo. A checagem prova a identidade da fixture nesta bancada; não mede autorização entre tenants nem produção.

2. **Estado de UI e URL:** `authentication.ts:67` exige o heading `Olá! 👋`; em `:70-72`, o pathname tem de ser `/inicio`. Não há aprovação baseada apenas no HTTP de login ou na existência de cookie. O assert final de URL é síncrono após o marcador de UI.

3. **Contrato de hidratação:** `src/routes/auth.tsx:121-129` faz a consulta de sessão no `useEffect`, após o commit de React que anexa os handlers do formulário. O helper atual acompanha `framenavigated` no frame principal para `/auth`, captura o Request GET posterior a esse evento e aceita somente a Response desse Request (`authentication.ts:11-35`). Os listeners são removidos no `finally` (`:36-39`). Isso resolve o caso concreto de uma resposta pendente do documento anterior. O contrato é razoável para o código atual de `/auth`; se o aplicativo retirar/mover essa consulta, o helper deverá ser revisto, pois essa é sua condição observável de prontidão.

4. **Negativo não vacuoso:** `authentication-gate.spec.ts:22-29` intercepta somente `pushState`/`replaceState` cujo destino é `/inicio`. Preserva rede, credenciais, sessão e renderização. `:32-39` exige especificamente a rejeição `Authenticated navigation must end at /inicio`, a URL `/auth` e o heading autenticado visível. Um login rejeitado ou timeout do heading não satisfaz essa mensagem. O TanStack History instalado mantém uma localização lógica otimista antes de executar a History API (`@tanstack/history/src/index.ts:398-424`); isso explica por que a shell pode renderizar enquanto a atualização do endereço fica suprimida. O mutante exercita a falha de atualização de endereço após login, não uma substituição completa de `navigate` por no-op.

5. **Timeout e gates:** a espera inicial e a resposta de sign-in continuam em `5_000` ms. O heading usa a espera de locator padrão; não há sleep fixo, retry de login ou ampliação de orçamento. O teste de controles acessíveis continua usando o helper no mesmo ramo `browserName === 'chromium'` (`ui-stack.spec.ts:111`, que também abrange o projeto mobile com Chromium). Configuração e regras de rate-limit não foram afrouxadas.

6. **IPs e rate-limit do novo controle:** os IPs negativos `.21-.24` são distintos entre os quatro projetos e dos IPs fixos `.10-.14` usados pelo setup e projetos. O limite continua habilitado, armazenado em banco e em cinco sign-ins por 60 s (`auth.server.ts:87-97`; `rate-limit-rules.server.ts:5`). O Better Auth instalado usa `x-forwarded-for` e chave `IP|path` (`@better-auth/core/dist/utils/ip.mjs:194-238`; `better-auth/dist/api/rate-limiter/index.mjs:234-269`). A API `page.request` conserva os headers do BrowserContext, não o override da página: o GET de sessão do negativo permanece no IP do projeto, mas é outro bucket de endpoint; o POST da UI usa o IP negativo. Isso não consome sign-in do projeto pelo novo GET. O delta de vendas atual usa `203.0.113.1-.4`, explicitamente disjuntos dos IPs de setup/projetos/negativos, e contém três sign-ins por projeto em uma execução completa. As quotas continuam sendo estado compartilhado do banco: repetição de bancada exige estado inicial conhecido; este parecer não certifica quotas limpas entre execuções.

7. **Mensagens do delta:** os novos asserts expõem apenas nomes de variáveis, status HTTP, booleano de identidade, heading e pathname. Não interpolam senha, cookie, token ou corpo de resposta. ## Achado concreto corrigido durante o review

**[P2] R1 — resposta da página anterior podia estabelecer prontidão da nova página.** A primeira versão (`authentication.ts:11-18`, SHA-256 `d20e70f544c00b24dafb1e4948dd60545757a7b79f4feb62d023020ccd1843ad`) aceitava qualquer Response GET com pathname `/api/auth/get-session`, antes de `page.goto('/auth')`. O caller de controles acessíveis já vinha de `/auth`, e o próprio Auth emite esse GET. Portanto o filtro não distinguia uma resposta antiga ainda pendente de uma consulta iniciada após a nova navegação. Isso poderia liberar a interação com o novo HTML antes dos handlers estarem anexados.

Correção solicitada: vincular a prontidão ao request iniciado após a navegação do frame principal e comparar a identidade da resposta, sem aumentar timeout ou tocar no app. A versão atual relida faz essa atribuição em `:11-35` e remove os listeners em `:36-39`. **Estado: corrigido por inspeção de código; execução da versão final cabe ao autor.** A medida inicial e final dos hashes foi executada nesta revisão.
