**Diagnóstico declarado da recusa do passo 6 e fix local (2026-10-08, bytes WIP sobre `2875382b`):** o
loop de readiness do provisionador só esperava a **branch** — o endpoint `read_write` recém-criado
pode seguir em `current_state: "init"` quando a branch já reporta `ready`, e o `connect()` contra ele
falha em ~0,5 s (warning do `pg` → recusa), antes de qualquer SQL; o `catch` sem parâmetro
distinguia connect de SQL de identidade; e o drop-set despejava **todos** os schemas descobertos,
inclusive os geridos pelo Neon (`neon_auth`/`pgrst`, SQLSTATE 42501 latente). O fix: (a) o loop
polla branch **e** endpoint conectável (`active`/`idle`; corrigendum pós-run 37731806892 — o enum
real de endpoint é `init`/`active`/`idle`, sem `ready`; `idle` acorda ao conectar) sob os mesmos
predicados de branch/projeto/tipo/disabled/host; (b) o drop-set passa a ser exatamente os schemas que a cadeia de
migrations cria/rebuilda (`app_private`, `drizzle`, `public`), os geridos são mantidos
verificados-vazios e devolvidos em `keptSchemas`; (c) o prepare rastreia
`identity`/`connect`/`prepare`/`persist` e projeta **uma** linha sanitizada
(`Neon fixture refused: phase=…, code=…; no credentials logged`) com código validado
(`[0-9A-Z_]{5,12}`, senão `none`), gravando artefato de falha `neon-pr-fixture.json`
(NO-VERDICT) somente inexistente, sem mascarar a recusa original. RED→GREEN local medido —
**18 falhas / 73 passam** em 91 → **91/91**, exit 0.

**Causa raiz da recusa diagnosticada e corrigida nesta linhagem:** a API do provedor anexa
`channel_binding=require` ao lado de `sslmode=require`, e a allowlist de query do validador admitia
apenas `sslmode`. O fix passa a aceitar a allowlist validada `{sslmode, channel_binding}` (valores
`require`/`verify-ca`/`verify-full` e `require`/`prefer`/`disable`), preservando a propriedade de
segurança: nenhum parâmetro movedor de destino (`host`, `hostaddr`, `port`, `options` ou chave
desconhecida) é aceito e a porta 5432 permanece explícita. **Aceitação do CI pós-fix OBSERVADA até o passo 6 (run 37722430962, head `2875382b`):** provisionamento e identidade do filho passaram; a preparação da fixture recusou (exit 2 sanitizado) e a cadeia restante segue `skipped`; `DBT-96` continua ABERTA.

`init_source: "parent-schema"` (CHILD) respondem HTTP 412 (runs `37556250921`, `37634147956`,
`37700582228`; request de console `bba50fbd-1e38-49d7-a52b-084e5b6e95ed`). O `parent-data` é
aceito. O dono autorizou uma base permanente e vazia — `ci-fixture-base`
(`br-wandering-sky-ayxm5e5s`), filha `parent-data` de `production`, criada uma vez e esvaziada uma
vez (BEFORE 15 tabelas / 162 linhas → AFTER 0 / 0, 0 grandes objetos, prova in-band
`neon.branch_id`) — e cada PR passa a criar um filho `parent-data` de zero linhas dessa base. O id
da base entra em **todos** os guardas e relatórios de permanentes: é impossível tratá-la como
recurso descartável e o cleanup nunca pode apagá-la. `init_source`, pai, payload, guardas e
relatórios foram atualizados em RED→GREEN; o gate completo foi medido em bancada limpa. A
recusa do primeiro run real (URI) foi rastreada até a allowlist de query e corrigida com novo
RED→GREEN local; o CI real destes bytes ainda não existe.
