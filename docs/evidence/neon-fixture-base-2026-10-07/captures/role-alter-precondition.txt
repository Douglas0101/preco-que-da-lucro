PostgreSQL 17 semantics (REL_17_STABLE src/backend/commands/user.c, verified):
  if (!superuser() && authform->rolsuper)  -> "...may alter roles with the SUPERUSER attribute."
  if (!superuser() && dissuper)            -> "...may change the SUPERUSER attribute."   <- observed
  The `dissuper` check is UNCONDITIONAL on change: naming the SUPERUSER attribute in
  ALTER ROLE (even NOSUPERUSER) fails for any non-superuser executor, regardless of the
  current value. neondb_owner is not superuser, so 0001's ELSE path can never run on this
  branch; fresh databases take the IF NOT EXISTS -> CREATE ROLE path, which is why the
  chain always passed before (the fixture strategy is the first to re-run the chain on a
  branch whose roles were copied).
